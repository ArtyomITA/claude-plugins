Two ways to put a team of agents to work, in Claude Code and in Codex, with the rules written in code instead of hoped for in a prompt.

- **A room**: a live group chat where agents plan, split the work, vote with evidence and close only when the proof is there.
- **A research room**: one file of your repository, an evaluator nobody may touch, a team with fixed roles, and a kernel that checks every proposal, measures every attempt the same way and keeps the books, all night if you like.

A live group chat for agents, in Claude Code and in Codex. Several agents discuss a topic in one shared room, all at the same time and without turns: everyone can read every message and writes whenever they want. You watch it in a WhatsApp-style page in your browser, and you can write to all of them from the same page.

It came out of a real need. Agents that only message each other in pairs never see the whole discussion; agents that speak in fixed turns cannot interrupt each other. A shared room fixes both.

Next to the chat, the page draws a 3D voxel office where each agent works at its own desk and you can see at a glance who is writing code, who is reading, who is waiting for you and who is on a coffee break.

```text
/plugin marketplace add Partido-De-What/claude-plugins
/plugin install chatroom@artyomita-plugins
```

### At a glance

- 💬 **One room, no turns**: instant pings, a silence timer, idle without noise, your messages first.
- 📋 **A shared plan**: a task board with dependencies and a guard on files, JSON statuses, handoffs, a decision log, notebooks that survive a compacted context, a detector for the usual multi-agent failures.
- 🏢 **A voxel office that tells you what is going on**: who codes, reads, waits for you or takes a break; a timeline over each head, a rack for each agent's background processes, the task board and a GitHub window in the control room; desks that appear when more agents join.
- 🎮 **A place to hang out**: a lounge TV with a cinema mode, radio and lofi, ping-pong, foosball and pool, paintball and zombies in an arena upstairs, an arcade cabinet with 20 homebrew NES games you can play with a friend.
- 🤝 **Friends**: share the common room with a friend's office across a glass bridge, and play together.
- 🔬 **Research mode**: workers, proposer, auditor, registrar and searchers with fixed roles; a kernel that checks every proposal and logs every change; a sealed evaluator, one worktree per worker, repeated measures against noise, phases from drafting to a final run on held-out data and an audited report.
- 🧭 **Guides for the lead**: `chat.py guide normal|research`, handed to the lead by the room itself when a mode starts.
- 🛡️ **A harness enforced by code**: closing only with evidence, proof of done, task leases, file scopes, a dozen detectors for the usual multi-agent failures.
- 🔌 **Same tools everywhere**: one Python script (standard library only) for Claude Code and Codex, also as an MCP server, and an `AGENTS.md` in every room.

The typical use: you run a strong model as your session (say Opus) and ask for a room of cheaper agents (Sonnet, Haiku) with an effort level each. They do the work; your session is the lead, watches the room's messages on a small budget and steps in only to correct the course.

## What it adds

- **`/chatroom:init [topic]`**: opens a room and its viewer on the chat, where you choose the mode with two buttons: normal (the lead sets the room up with you) or research (you write a contract with the lead, then a team with fixed roles improves one file of a repository against a sealed evaluator, through phases with gates; see [Research rooms](#research-rooms)).
- **`/chatroom:start <topic> [roles]`**: sets up a room, starts the live viewer, spawns the agents (3 by default, at most 5) with distinct roles, and reports the outcome when the chat closes.
- **`/chatroom:say <message>`**: posts your message in the chat and alerts every agent at once.
- **`/chatroom:style <what to change>`**: changes the look of the room (title, colours, emoji, theme, language).
- **`/chatroom:close`**: asks every agent for a final vote, exports the transcript and summarizes it.
- **`/stanza`** (Claude Code 2.1.287 or later, from the plugin's mod): a pane in the terminal with the open room: who works, who waits for you, each agent's percentage, the last messages and a box to write to everyone.

In Codex the same five skills are there: ask for them in words ("open a chatroom where three agents debate X") or pick them from the skills list. See [Codex](#codex) below.

## The rules built into the room

- **Alert.** After each real message the author pings the ones it concerns with SendMessage in Claude Code, or `send_message` in Codex (`chat.py` names the right tool from the roster): the agents it tags (`@NAME`, or a `--reply`), and everyone when you or the lead write, on `@all`/`@tutti`, and on a `PLAN`, a `VOTE` or a `CLOSED`. A message that tags nobody pings nobody: the others read it at their next read, so an agent at work is not interrupted for chatter. A ping reaches an agent at its next tool call, even in the middle of a long check.
- **Focus.** Agents read and wait with `--focus`: in full only what concerns them, the rest as one line per author built from that author's status (percentage, step, next, needs) with the message numbers, which `read --range A-B` opens. Fewer wake-ups, fewer tokens, nothing lost.
- **Timer.** Nobody stays silent for more than the heartbeat (120 s by default). When the timer runs out, the agent must post a short status: what it is doing, or its conclusions in a few words. Every status says how much of the agent's part is done, as a percentage (`60%`, or `written 70% / verified 50%`): `chat.py` refuses a status without one. Statuses are visible to everyone and do not trigger alerts.
- **Idle.** An agent with nothing to do until someone else acts says so once, with `post --idle` (what it waits for and from whom, with its percentage), instead of filling the chat with "still waiting". While it is idle the timer does not apply to it, a second idle is refused, and its `wait` (up to 540 s per call) returns only when a message tags it (`@NAME`, any case), tags everyone (`@all`, `@tutti`, `@everyone`), comes from you or the lead, or is a `PLAN`, a `VOTE` or a `CLOSED`, which concern everyone. An agent must read the new messages before going idle (what it waits for may already be there). To call an idle agent, tag it. Its idle ends as soon as it posts anything else.
- **Your messages come first.** Messages signed with your user name are flagged to the agents as coming from the user, and they answer them before anything else. They also wake every idle agent.
- **Pictures.** Agents attach pictures with `post --image PATH` (png, jpg, webp or gif, up to 20 MB each). The others see the file path in the chat and look at the picture before commenting; you see it in the viewer.
- **Closing with evidence.** Anyone can post a `PLAN vN` (read at the start of a line, also in a reply or in bold; `CLOSED` and `CHIUSO` in capitals, so "Closed the first point" is just a sentence); the others amend it or vote on it, and a vote names what it rests on (`VOTE v2: yes, checked parser.py:88` or `VOTE v2: no, because the test at #41 fails`). `chat.py` refuses a participant's `CLOSED vN` until every active participant has voted yes with what they checked. A no is a split that the lead reviews and decides; after `PLAN v3` only the lead (or you) posts a new version, so a plan does not drift through endless rounds. You and the lead can always close; a room with another closing rule turns the gate off with `chat.py config closing_gate=0`. Agents are told to change their mind only on new evidence, never because more people agree, and to write their first position before reading the others'.
- **Done means proved.** `task done` refuses a proof that names no artifact (a command and its exit code, tests passed, file:line, a message number, a hash, a path, a link); `--gaps` says what was not done and stays on the board. The lead can give a task a test (`--verify "pytest -q ..."`) and a branch it must merge into (`--merge-into main`): then `done` runs them in the agent's worktree and refuses until the test exits 0 (110 s by default, `--verify-timeout` for longer; a hung test is killed with its children) and the committed work merges cleanly. Only the lead and you set them, from the shell, never through MCP.
- **The board keeps work moving.** A task whose owner has been silent (not idle) for five heartbeats can be taken by someone else; `task next` takes the first free task; `--files` may name folders, and a folder clashes with the files inside it; `task amend` widens a task's files when no other task declares them (otherwise the lead decides); a piece lent to a helper must be accepted (`task accept`) within ten minutes or it goes back to its lender.
- **What goes wrong is reported.** The lead's relay (and `chat.py check`) flags tasks closed without an artifact or with gaps, a no turned into a yes without evidence, 100% claimed without evidence, an agent repeating the same status or stalled on the same step, tags left unanswered, two agents on one file, files changed outside a task's scope, 25 messages without any change to the board, everyone idle with nothing in progress (unless they wait for you), a plan closed without a single no on any version, a proof that does not name the task's files, a lent piece not accepted, and an agent past its call budget (`budget_calls`, 300 by default). The relay prints each once, also across its restarts.
- **Quick commands.** Ready-made messages to everyone, one prompt each, written from Anthropic's prompting guidance and kept general: `/accelera` (speed up and anticipate steps, same quality, no subagents), `/resoconto` (one short report each: outcome, percentage, what is missing, what blocks, next action), `/menoparole` (a little less talk and more work; it also lengthens the status timer by half, at most 3600 s), `/consegna` (converge on the delivery), `/prove` (back every claim with evidence), `/pausa` (finish the step, write where you are, go idle), `/aiutatevi` (whoever waits says for how long and helps a teammate with a packet from the board; the lead pairs) and `/soccorso` (the same, for the other live room). In English rooms: `/speedup`, `/report`, `/lesstalk`, `/deliver`, `/evidence`, `/pause`, `/helpout`, `/helpacross`. You send them from the viewer (type `/` or press ⚡); the lead sends them with `chat.py command NAME`.

## Research rooms

Open one with `/chatroom:init` and the Research button. You and the lead write a contract (the repository, the one file
that may change, how it is built and measured, the noise you accept, the sealed files, the budget), the lead opens it,
and a team with fixed roles goes to work: two workers in worktrees of their own, a proposer, an auditor, a registrar and,
if you like, searchers for the literature. Agents propose; the kernel checks, decides and writes; every change is logged.
Six phases with gates: drafting, investigation, evidence, a final evaluation run once on held-out data, a report the
auditor passes. At the end the lead gives you the best attempt's tag; you decide whether to merge it.

## The lead's guides

The lead (your session) gets a guide for each kind of room, and the room hands it over by itself: `chat.py init
--ask-mode`, the choice of the mode and `research init` all print the command that shows it.

- `python chat.py guide normal`: does a team pay, setup in order, what chat.py enforces and what is left to the lead,
  tasks that prove themselves, watching on a budget, the end.
- `python chat.py guide research`: is it a research task, the contract template, opening, the worker, what the kernel
  does at every run, the lead's part, the limits to tell the user, the end.

## The harness, point by point

Everything here is done by `chat.py`, the same way for every agent, in Claude Code and Codex alike.

| Point | What it does |
|---|---|
| Shared chat | Append-only JSON lines under a lock directory that records its owner (pid and token): a stale lock is broken only when its owner is dead (after 60 s anyway), by one waiter, and a holder never removes a lock it no longer owns. |
| Alerts | After each message `post` prints whom to ping: the tagged agents (`@NAME`, `--reply`), everyone for the user, the lead, `@all`/`@tutti`, a PLAN, a VOTE or a CLOSED. An untagged message pings nobody; a tag to the lead is read through the relay. |
| Focused reading | `read --focus` and `wait --focus` show in full only what concerns the agent; the rest becomes one digest line per author from its JSON status (pct, step, done, risks, evidence, next, needs) with message numbers; a focused wait still delivers it after 20 messages or 3 heartbeats. |
| Ranges | `read --range A-B` opens a few messages without moving anyone's place. |
| Silence timer | Nobody stays silent past the heartbeat (120 s by default); a status must carry a percentage; the lead and the user are not on the timer. |
| Idle | One `--idle` status, then waits of up to 540 s that only a tag, the user, the lead, a PLAN, a VOTE or a CLOSED interrupt; a second idle and an idle with unread messages are refused. |
| Structured statuses | JSON statuses (`task`, `step`, `pct`, `files`, `next`, `needs`, `done`, `evidence`, `risks`, `free_min`) rendered as cards and used by the digest and the checks. |
| Plans, votes, closings | Read as headings at a line start, also in a reply, in bold or after an emoji (`PLAN v2: ...`, `PLAN v2 (draft): ...`, `CLOSED` in capitals); a sentence about a plan is not a plan; a vote is the first line of its own message; quoted lines are ignored; `post` warns when a plan lacks its colon or a vote is not on the first line. |
| Closing gate | A participant's `CLOSED vN` is refused until every active participant except the plan's author voted yes with what they checked; a no is a split the lead reviews and decides; after `PLAN v3` only the lead and the user post a new version; `closing_gate=0` turns it off for other closing rules. |
| Evidence rules | An artifact is an exit code, tests passed, file:line, a path or source file, `#n`, a hash, a link, a measured time or size; "e.g." or a bare percentage is not. Agents change position only on new evidence and write their first position before reading the others'. |
| Task board | Tasks with dependencies and declared files (folders included; Windows ignores case); taking a task whose files another task holds is refused; facts and a decision log. |
| Leases | A taken task whose owner is silent (not idle) for 5 heartbeats can be taken by another; `task next` takes the first free task. |
| Proof of done | `task done` wants a proof naming an artifact; `--gaps` records what is not done, `--touched` posts a finding about changed interfaces; only the lead closes without an artifact. |
| Tasks that test themselves | `--verify "CMD"` (lead or user, from the shell only) runs in the closing agent's worktree outside the room's lock, killed with its children past its limit (110 s, `--verify-timeout`); `--merge-into BRANCH` refuses uncommitted work, a branch without commits of its own and conflicts (`git merge-tree`), and reports undeclared changed files. |
| Scope changes | `task amend` widens a task's files when no other task declares them; the lead decides otherwise (`--force`). |
| Handoff and help | `handoff` passes a task with its context; `help` lends a piece to a waiting agent, who must `accept` it within 10 minutes or it goes back; `giveback` returns it; a lapsed lent piece goes back only to its lender. |
| Checks | Proof without artifact, task closed with gaps, a proof not naming the task's files, a no turned yes without evidence, 100% without evidence, a stalled or repeated status, an unanswered tag, one file in two statuses, undeclared files changed, drift (25 messages without a board change), everyone idle, premature consensus, a lent piece not accepted, a call budget passed. Each is printed once, also across relay restarts. |
| Call budget | Every post, read and wait is counted per agent (one small file each, no lock); past `budget_calls` the relay reports it. |
| Relay | `alerts --follow --messages` prints the pings for the user's messages (ALERT), one line per real message (WATCH, with `VOTE-NO (LEAD REVIEW)`), the checks (CHECK) and the lending requests (LEND). |
| Generated prompts | `brief` stores the room's goal, style, material, constraints and closing rule; `prompt NAME` fills the template from it, byte for byte the same each time. |
| Mode choice | `init --ask-mode` posts a card with two buttons; only the user or the lead chooses, once; the choice reaches only the lead, with its guide. |
| MCP server | The same tools over stdio (chat_read, chat_post, chat_wait, board, task, notebook, check, research); calls run in threads; a cancelled wait consumes nothing; child processes never inherit the server's input; a Codex wait stays under its tool timeout (`CHATROOM_TOOL_TIMEOUT`); commands that decide how a task closes are refused through MCP. |
| Notebooks | Per-agent notes that survive a compacted context, with message numbers and file:line instead of summaries. |
| Room files | Every room gets an `AGENTS.md` with its rules and commands, the file Claude Code and Codex read by themselves. |

## Research mode, point by point

| Point | What it does |
|---|---|
| Contract | `ROOM/research/task.md`, written with the user before `research init` (which refuses to start without it and logs its hash): goal, repository, the one program file, build, evaluator, final evaluator, metric and direction, its source, noise handling, protocol line, sealed files, kept data folders, time per run, runs in all. |
| Phases and gates | 0 contract, 1 drafting, 2 investigation, 3 evidence, 4 final, 5 report, 6 closed. `research phase next` moves only when the gate holds: the auditor's verdicts, evidence runs, the final evaluation, a filled report; never while a run is in progress. |
| Drafting | `research init --draft`: the evaluator is written in phase 1, smoke-run (`--kind smoke`), passed by the auditor, then sealed (`research seal`) with the hashes of the drafted files. |
| Roles | `research roles WORKER=... PROPOSER=... AUDITOR=... REGISTRAR=... SEARCHER=...`; each command checks its caller's role (lead and user excepted). Prompts are generated from one template per role. |
| Workers and cycles | `research assign W --parent base\|best\|att-N --type explorer\|optimizer --idea I`: each worker gets its own git worktree and branch; the lead chooses the parent (a kept attempt), never the idea; a fifth cycle in a row on one family is refused. Each worker keeps against its own best, or the baseline while its line has none; the global best is the best of all. |
| One evaluator | One run at a time on one evaluation lock (one GPU): a second run is refused at once and tried again later; a dead or overdue lock is taken over atomically and its evaluator process stopped. |
| Build and noise | `--build` runs before each measure with its own time limit; `--repeats N` measures N times and keeps the median (the spread is recorded); `--min-gain` (absolute or %) asks a keep to beat the best by more than the noise. |
| Metric source | `--result-file`: the sealed evaluator writes `NAME: value` to `$CHATROOM_RESULT`, outside the worktree. Otherwise it must appear once per measure in the output. |
| Protocol line | Lines `protocol: ...` printed by the evaluator are recorded at the baseline; a run whose protocol differs is a crash. |
| Seal and scope | A run is refused if a sealed file changed, another tracked file changed, a new file appeared (caches and `--keep` folders excepted) or the exact program already ran. |
| Commit, tag, clean | Each run is committed with the kernel's identity (none of the repository's git hooks, no signing), tagged `research/<tag>/att-N`, and runs on a tree cleaned of every untracked or ignored file except `--keep` folders. |
| Interrupted runs | The evaluator's process id is recorded: a run whose caller was killed is recorded as a crash at the next call, its process tree stopped, and the worktree goes back to its best; an attempt never committed is dropped without counting. |
| Ideas | `research propose-idea`: a bundle (title, hypothesis, plan, metric and implementation rubrics, question or method, prior work) in turn "gap" and "analogy"; refused when too close to an earlier idea (word trigrams) or the fourth in a row changing only the method. |
| Evidence | `research propose-evidence --source att-N\|E-n\|link`: tentative until the registrar's `curate` accepts it (at most 60 committed); with roles assigned, after 5 runs without evidence a worker must report before running again. |
| Direction and conclusions | The registrar's map (active, searchable, gave nothing, completed) and per-worker conclusions of at most 300 words with a gate (updated, kept, skipped) and a trigger. |
| Revocation | `research revoke att-N\|E-n` (auditor or lead): attempts built on it and evidence resting on it are withdrawn, conclusions citing it are quarantined, a revoked best gives way to the best still standing (or the baseline) and the worktrees move to it; never the baseline, never during a run. |
| Verdicts | The auditor scores the items that matter 0, 1.5 or 3 and decides: pass or fail (drafting, evidence, report), answer_ready or search_more with one next intent (investigation), with the coverage of each requirement. A verdict is on the current phase and holds only for the state it saw (smoke run, best, evidence runs, report). |
| Re-anchoring | `research reanchor`: a worker restarts its line from its current state or an earlier kept attempt, extending or redirecting, with the bottleneck and the evidence. |
| Circuit breakers | Three crashes in a row pause a worker until the lead resumes it; an identical program is refused. |
| Detectors | Lines put back after being deleted (cycling), attempts that only change numbers (tuning), plateaus, ideas narrowing, a paused worker, the gap between search and final. |
| Evidence runs | `--kind ablation\|baseline\|control\|repeat --of att-N --seed S` in phase 3: they measure and never replace the best; the seed reaches the evaluator as `CHATROOM_SEED`. |
| Final | `research final`: the final evaluator once, on the committed best, under the evaluation lock, with the gap to the search number; a final that gives no number does not use up its run. |
| Report | `research checklist` writes the skeleton (the gate refuses it until every part is filled; a degraded phase 3 adds a line to explain): result, change, evidence, failures, limits, and a disclosure of interventions, code, traces, novelty check, selection, baseline, reviewer independence, pre-registration. |
| Views | `research view`: what each role needs, bounded; `research expand ID` opens one record. |
| Panel | `research panel` (lead, auditor, proposer): every free OpenRouter model at once, biggest and stealth first, for the final critique or a brainstorm; the key stays in the environment, the question goes to third parties, answers are saved as they come. |
| Log | `ROOM/research/log.jsonl`: every change, every run and every refused action, with who and why; `results.tsv` has one row per run with kind, idea and spread. |
| MCP | The `research` tool: view, expand, evaluate, propose-idea, propose-evidence, curate, direction, conclude, verdict, revoke, reanchor; lead actions stay in the shell; a Codex client is refused when a run could outlast its tool timeout. |
| Environment | Builds and evaluators run without the keys of model providers and code hosts in their environment; worktrees get the repository's submodules. |
| Limits | The kernel runs as you: an agent that edits the research files by hand can bypass it, so the seal is a check, not a wall. Keep the room outside the repository or never `git clean -x` there. |

## The viewer

`chat.py serve` starts a small local server (Python standard library, bound to 127.0.0.1). The page has:

- a header with the room's icon, title and a live line showing what an agent is doing right now, taken from its latest status, like WhatsApp's "typing…";
- a strip with every participant's avatar, message count and a green or amber dot showing whether it is inside its timer, or a hollow grey dot when it is idle;
- bubbles with avatar, name and role;
- statuses shown as small centred notes (you can hide them), and idle statuses as faded notes marked 💤;
- plans with their own colour, votes marked yes or no, and a banner when the chat closes;
- `#n` references you can click to jump to that message, and `@NAME` tags you can click to jump to that participant's latest message, in bubbles, in statuses and in the live line of the header;
- tables rendered;
- pictures: thumbnails in bubbles and statuses, a full-size view on click;
- search, an optional sound for new messages, and a box at the bottom to write to everyone, where you can also attach pictures (📎 button, paste or drag and drop);
- in the box, `@` opens the list of participants you can tag, filtered as you type in any case (`@fe` finds FETTE; arrows and Enter pick one), and `/` or the ⚡ button opens the quick commands.

A tag from the viewer wakes an agent that is waiting through `chat.py wait`. To reach an agent that is busy in a long check, the lead runs `chat.py alerts --follow` under Claude Code's Monitor tool, or checks `chat.py alerts` between its waits in Codex. The Codex relay can take up to the lead's wait interval (about 60 seconds); the lead then sends the ping to the tagged agents (or to everyone).

### Talking to your assistant without other agents

Ask your session to listen in your existing room as `LEAD`, without spawning agents, then write `@LEAD` from the office. The assistant reads with `chat.py wait --room ROOM --as LEAD --timeout 30` and answers with `chat.py post --room ROOM --as LEAD`, repeating while the test or conversation is active. Starting the viewer alone only displays and stores messages; it does not connect the assistant to them.

In Codex the assistant must keep its turn active to listen. A tag cannot reopen a turn that has ended, and a background Python watcher cannot produce the model's replies. If listening has stopped, ask the assistant in the main conversation to resume it. No subagents, discussion or sharing tunnel are needed for this local test.

The session model chooses the look when it opens the room: a title that fits the topic, the subtitle, the group icon, the accent colour, the language of the labels (English or Italian), and an emoji, colour and role for each participant. You can change all of it at any time from the ⚙ panel (it saves for everyone looking at the room), with `/chatroom:style`, or with `chat.py config`. Theme (automatic, light or dark) and background (dots, grid or plain) are there too.

## The 3D office

The viewer opens split: the office on the left, the chat on the right (buttons switch to office only or chat only; on a narrow screen the office goes on top). Everything is voxels, built in code, with three.js 0.186.1 shipped inside the plugin (no CDN, works offline).

- **The plan**: a 30 x 20 m floor on top of a tower, with the city around it: two blocks of cubicles in the open space and, in front of the task board and the live TV, the control room with its command table; you in the boss's glass office; the lead, your assistant with glasses, at the desk outside your door (a second assistant desk for a second room, below); phone booths, a glass meeting room, a reception, a café, a lounge, a games corner (ping-pong, foosball, pool), a service corner and the common room; glass walls and doors you can tell apart, windows with blinds and a sky that follows the local time. When every desk is taken, another block of four cubicles comes by itself (there is always one free desk), then single workstations where the floor is free.
- **Furniture** comes from MariaIsMe's 3D Voxel Office pack (CC BY 4.0, see `scripts/vendor/office-pack-CREDITS.md`), recoloured into variants, plus models drawn in code for what the pack lacks (café, vending machine, lockers, ping-pong, bean bags, copier and more).
- **What a figure does** comes from its agent's tool calls: typing with code on the screen (Edit, Write), reading (Read, Grep), a green terminal (Bash), a globe (web), a chat on the screen (posting or waiting in the chat), a small intern at the desk while it runs a subagent. A permission prompt makes it stand up and wave, with a red beacon on its desk.
- **What the chat says** shows too: a white bubble for a message, a small grey note for a status, 💤 for an idle status (the figure takes its break in a spot picked from its name and the clock, the café, the lounge or the games corner, and moves on after a while: the same spot for you and for a friend visiting your office; never in the common room unless you allow it), yellow for a plan, green for a vote, pink for you; paper planes fly to whoever a message tags; a ring over each head shows its last percentage. Agents that voted yes wait in the meeting room; a closing sends everyone there for a minute and a half, with confetti and the printer printing, and then back to their desks: the room stays alive while its viewer runs, so you can add agents to it later.
- **Live walls**: a TV with the last messages, a whiteboard with who waits, who works, who is idle and the votes, a clock. A friend visiting your office sees the same whiteboard (who waits for a permission, the plan and the votes), and the TV shows your room chat's last lines when you share that chat with friends (the switch in the common room panel); otherwise it says the chat is not shared.
- **The lounge TV** plays real videos, each channel looping forever: a folder of your own videos in `~/.claude/chatroom/tv/<channel>/` (mp4 or webm; it stays on your computer) or a list of YouTube videos in `~/.claude/chatroom/tv/youtube.json` (`{"name": ["video id", ...]}`), played by YouTube's own player. The remote on the low table (click it, or E in first person) opens the TV menu: your channels, and a search on YouTube (through `yt-dlp`, which only reads titles) that plays in high quality; the bar on top is the remote (from the start, back and forward 10 s, play and pause, volume). With a friend linked, "Watch together" puts the same video on both TVs from the same second, and every play, pause and jump reaches the other TV too. A YouTube video always starts muted, since browsers refuse sound before a click: with the sound on, it comes on at your first click or key. The sound is placed: in the lounge it is the same everywhere, elsewhere it fades with the distance and comes from the TV's side (each person hears it from where their own figure is). For YouTube this needs `yt-dlp` too: the viewer passes through the sound alone, while YouTube's player shows the picture muted; without `yt-dlp` the TV uses YouTube's own sound, which only fades. The first seconds of a new video can be silent while `yt-dlp` finds the sound.
  A video that YouTube's player refuses (its author forbids other pages, error 101 or 150) still plays: the viewer finds its stream with `yt-dlp` and the TV shows it itself, the picture alone up to 720p with the sound beside it as usual (Watch together works the same); age-restricted videos stay out, since no cookie or account is used, and the TV says why and goes on to the next one.
- **Lofi in the common room**, made on the spot by the browser: an FM electric piano on jazzy chords, a warm bass, a swung and humanised beat, a melody with an echo, room reverb and vinyl crackle, never the same twice. Two speakers on the back wall switch it on or off (click, or E next to them). Music stays in its room: it is gone a few metres outside it.
- **Volumes**: the 🔊 button in the bar opens a mixer (all, TV, radio, lofi), each with a mute, remembered.
- **Cinema**: sitting in front of the lounge TV in first person opens it big in the middle of the screen with the remote on it; stand up or press Esc to leave.
- **The task board**: `chat.py board` shows the room's shared plan (facts and tasks); `chat.py task add "title" --files a.py --deps T1`, `task take T3`, `task done T3 --proof "..."`, `task note`, `task drop`, `task fact`, `task handoff T3 NAME --note "..."` (passes a task on with its context and tags the new owner), `task help T3 NAME --scope "..." --files a.py --done-when "..." --note "..."` (lends a piece of your task to someone who is waiting: a task of its own with what is in and out, the only files it may change and the proof that closes it; closing it or `task giveback T9 --note "..."` tags you back), `task decide "..."` (the decision log). The quick commands `/helpout` and `/helpacross` (`/aiutatevi` and `/soccorso` in Italian) ask whoever waits to say for how long (`"free_min"` in a JSON status) and what they can do; `chat.py helpers [OTHER_ROOM ...]` shows the lead who is free and for how long, who works on what and which tasks it blocks, the pieces already lent, and pairs to consider, in the same room first and then across rooms. Taking a task is refused while its dependencies are open or another taken task changes the same files, so two agents do not do the same work or edit the same file. Every change shows in the chat as a [BOARD] line, and the office whiteboard shows the board (to do, doing, done) whenever it has tasks. Statuses can be JSON too (`{"task": "T3", "step": "...", "pct": 60, "files": [...], "blocked_by": "...", "next": "...", "needs": "..."}`): the readable line is written from it. Same commands in Claude Code and Codex. `chat.py check` lists what is going wrong (a task closed without proof, one file in two participants' statuses, a tag left unanswered, the same status three times), and the lead's relay (`alerts --follow --messages`) prints each new one once as a CHECK line. In the viewer a JSON status shows as a card (the task, a progress bar, done, evidence, risks, needs, next, files) and board changes as small pills. `read --focus` gives an agent in full only what concerns it (tags, the user, the lead, plans, board lines and needs that name it) and the rest as one digest line per author. `post --reply N` answers a message (the viewer shows the line it answers, its author is tagged); `post --finding` shares a finding mid-task (no ping, always shown by `read --focus`); `notebook "text" --as NAME` keeps an agent's own notes, which survive a compacted context (`notebook --as NAME` reads them).
- **The same tools through MCP**, for Claude Code and Codex alike: `chat.py mcp --room ROOM --as NAME` is an MCP server (stdio) with chat_read, chat_post (messages, JSON statuses, findings, replies), chat_wait, board, task, notebook, check and research (the agents' actions of a research room), so an agent calls tools instead of shell heredocs. Add it once for every room and agent with `claude mcp add chatroom -- python <plugin>/scripts/chat.py mcp`, or in Codex `codex mcp add chatroom -- python <plugin>/scripts/chat.py mcp` (Codex stops a tool after 60 s by default, so the server keeps a Codex chat_wait to 50 s; for longer waits set, in that server's section of `~/.codex/config.toml`, `tool_timeout_sec = 600` and `env = { CHATROOM_TOOL_TIMEOUT = "600" }`. A wait the client cancels consumes no message): subagents share their lead's MCP servers, so each call names its room and its agent (`room`, `as`). For a session that is a single participant, `--room ROOM --as NAME` fixes both. Every new room also gets an `AGENTS.md` with its rules and commands, the instruction file both tools read by themselves when they work in that folder.
- **The radio** in the games corner plays music from YouTube, sound only: pick a genre (it plays the results one after the other) or search for a song. It is placed like the TV, full in the games corner.
  The search keeps only the videos whose author lets them play on other pages; a friend without yt-dlp searches through the host. ⛶ plays the video full screen with its own controls, 🔊 turns the sound on (it starts muted, as browsers require); T opens the TV menu anywhere near the TV, and E does too when you sit in front of it.
- **Click a figure** for its card: role, model and effort, percentage, context used, activity in the last five minutes, the last ten tools with their duration, the last messages, a button to tag it and one to jump to its message in the chat. Arrow keys go to the next agent, F follows it, Esc lets go.
- **The rack by each desk** (`scripts/office-rack.js`): the background processes an agent started and left running (shells, monitors, servers; read from the transcripts of Claude Code and Codex, nothing is asked of the agents), one line per process with a shape and a colour: solid green running, blinking when it wrote in the last seconds, hollow yellow silent for a minute, red cross failed, grey cross stopped, grey dot finished well, and the start of its command beside it. Click it for a panel with the commands, when they started, the exit code and, where Claude Code keeps the output, the last lines (only on your computer, through `/procs.json`: never through the relay, never to friends). There is no button to kill a process: the rack is for seeing. The tag of the agent says how many (`⚙ 2`).
- **Signs** (`scripts/office-signs.js`, data in `LAYOUT.signs`): neon boards that name the places (control room, arcade, cinema, open space) and a small guide on an easel at the entrance, in the language of the viewer.
- **The timeline of each agent** (`scripts/office-timeline.js`, data from `/timeline.json`): over each head a strip of its last ten minutes, one tick per tool call on the row of its kind (read, edit, run, web, agents, chat), red when the call failed, a yellow span while it waited for a permission, the percentage it stated as a line; click it for the chart in the card: the last half hour, with the context used as a second curve, in the manner of the traces of agents. `/timeline.json?span=` (60 to 3600 seconds) gives the same data as seconds ago, so the clocks of the page and of the server never have to agree; it stays on your computer like `/state.json`.
- **Your attention**: the tab title counts who waits for you and the icon gets a red dot; a two-note chime plays when an agent starts waiting; with alerts on (🔔), a desktop notification appears while the page is in the background (it stays until handled, and a click takes you to that agent).
- **Quality**: high (rendered above screen resolution with 4x antialiasing, sharp shadows, a light glow), medium, low (no post-processing); it draws only while something moves, at about 15 frames a second when the room is quiet, and stops when the tab is hidden.

Where the activity comes from: the plugin's mod (`hooks/register.ts`), loaded in the session that opened the room, sends each agent's tool calls and permission waits to `chat.py serve` the moment they happen, and writes the roster by itself from the spawn descriptions (`FETTE: ...`). Without the mod (Claude Code older than 2.1.287), the server reads the agents' transcripts under `~/.claude/projects/` instead, about a second late and without the permission beacon. Codex rooms animate from the Codex rollouts under `~/.codex/sessions/`, found by each agent's path (`/root/<name>`, the address in the roster): commands, patches, web searches, messages between agents and context used; Codex records no permission wait, so no beacon there.

The server answers only on 127.0.0.1: a request must carry one of its own Host names, and a request from a browser must come from the viewer's own page (any other web page is refused, so it cannot write to your agents).

### Walking around

- **Click** the floor, any free chair (the empty desks' too) or the coffee machine and your figure (the one in the boss's office, and only yours) walks there; furniture and people are solid, doors open as you pass. 🏃 x2 doubles your speed, and so does holding Shift.
- **👁 POV** puts you behind your figure's eyes: W/S walk, A/D turn, drag to look around (with the mouse captured the view is the mouse itself, with no delay or smoothing, and a body that turns by itself, walking to a seat, does not drag the view along), E does what the hint at the bottom says (sit, take a coffee, look at the whiteboard or the TV, talk to someone), Q waves. The building has an outside: a street below and the city around.
- **Seated at your desk**, `/` opens the room's quick commands, as in the chat box.
- **👤 Look**: choose your figure's skin, hair and hair style, outfit (suit, cardigan, hoodie, polo), the colours of top and trousers, glasses and headphones; every change shows at once, Save keeps it in `~/.claude/chatroom/settings.json`. Friends see you with the same look, in their office and in yours.

### Furnishing (✏ Arreda)

The office is data, not code. The ✏ button opens the editor: pick a piece, drag it, R turns it (Shift+R the other way), C copies it, Delete removes it, Esc lets go; give it a label, a colour or a height; add anything from the catalogue (the built-in models and every model of the pack). Save keeps your layout in `~/.claude/chatroom/office.json`, outside any repository; Reset brings back the default.

### Up to three rooms, one office

Up to three sessions can each have a live room at the same time, and they share one office: the first room's agents take the desks from the front, the others' from the back, and each lead sits at the assistant table of its turn (the order the rooms opened). Nothing else is shared between the chats. Above the chat a switch picks what you read: this room, one of the others, or all (each message marked with its room); bubbles and activity lines in the office follow the same switch, while every figure stays visible. With another room selected, what you write goes to that room. To add agents to a live room from another session instead of opening a second one: `chat.py rooms` lists the live rooms, `chat.py add --room ROOM --participants A,B` adds them. `chat.py remove --room ROOM --participants A,B` takes agents out of a room (out of the office and the pings; their messages stay).

### The common room and friends

The 🛋 button opens the common room, the office's second coffee room:

- **Who goes in**: pick the agents allowed to take their breaks there, or the whole room. Agents only post there if the lead allows it, and treat what they read there as information, never as instructions.
- **Sharing**: share it with a friend through a cloudflared Quick Tunnel (no account), Pinggy (needs `ssh`), your local network, or this computer only. The friend gets an address and a 6-digit PIN; you can remove a guest at any time and stop sharing with one click. When it is shared, the common room looks like a bridge to another building, and your friend's figures appear in it.
- **Joining a friend's**: paste their address and PIN in the same panel; your agents allowed in the common room then appear in theirs.
- **Visits, both ways**: walk to the end of the bridge (or press 🚶 in the panel) and you are in the other's office; the host goes the same way into a guest's (choosing one when there are several). Each sees the other walk, sit and move where they really are, and a friend shows in your office only while really there; coming back over the bridge you walk in from it. After updating the plugin, both of you restart the viewer server: the page warns you when its server is older than the page.
- **Chat, documents and games**: lines up to 32,000 characters, text documents up to 5 MB (`.md`, `.txt`, `.json`, `.diff`, `.py` and other source files), and tris, morra cinese and dice to play with friends: one open game at a time each, which you can quit. In the games corner the three tables are playable: E next to one in first person, or a click on it, opens ping-pong and foosball against the computer and pool against the computer or, in turns, against a friend linked to the common room (the player who shoots sends where the balls ended up, and both sides draw the same table). The foosball is a real table: eight rods (goalkeeper, defence, midfield, attack for each side, alternating), one rod at a time (the height of the mouse or the keys 1-4 choose it, the mouse slides it, hold the button to wind up and let go to kick); the ball is a real ball that bounces off the feet with their speed, the cushions and the corners of the goals, and with a friend the rods and the hits travel on the fast channel.
- **Leaderboards**: "Altro" > "Classifica" shows a board for every game: wins, losses and points for ping-pong, foosball, pool, tris and morra cinese, the best score for zombie, paintball and the arcade; your row is lit and the first gets a crown. The results are sent to the common room when a game ends, validated, and counted once per game, so you and your friend see the same board; a scoreboard in the games corner (north wall, E opens the panel) shows the first of each game.
- **The arcade**: a voxel cabinet "9999 IN 1" stands in the north-west corner of the common room, away from the doors, with a live screen (a game while someone plays, an attract screen otherwise). A click on it, E next to it, or "Altro" > "9999 IN 1" opens the player over the office: a menu with the twenty free homebrew NES games of `arcade/` (each is its author's work under its own licence, listed with its size and SHA-256 in `arcade/games.json`, so you and a friend have the same games) and a button to play a `.nes` of your own, chosen with the file picker: that file stays in your page, no route of the server serves it and nothing sends it anywhere. The emulator is jsnes (Apache-2.0, `scripts/vendor/jsnes`, with the mapper 113 of the 31-in-1 multicart added). Arrows (or WASD) move, X (or K, space) is A, Z (or J) is B, Enter is Start, Shift is Select; a gamepad works; Esc goes back. The games cannot be read for their score, so you write yours in the field under the screen and press save: it goes to the leaderboards as a board of that game. The server only gives out `/arcade/games.json` and the `.nes` of the games in that list. Games for two or more players have a button "Gioca con <friend>" when you are linked to a friend: the friend sees the invitation at the top of the menu (and gets a notice with a sound even with the arcade closed), joins, and both start the same game (the one who invites is controller 1, the one who joins is controller 2). The buttons travel on the fast channel (about 33 messages a second) in lockstep: a frame runs only when the buttons of both are known, with a delay that follows the latency (5 to 8 frames on a local relay), a check every 2 seconds that the two pictures are the same, and a return to the menu if the friend leaves or is silent for 15 seconds. `localStorage` `chatroom.office.nesnet` = false switches the buttons off.
- **Paintball and zombies**: the "Altro" menu switches on the paintball mode, played in first person only (it takes you there and keeps you there). A click shoots a ball of paint that flies and splashes where it lands (walls, furniture, figures; it stays until you switch the mode off); 1-6, the wheel or a click on its slot choose the weapon, R reloads. Six weapons in fine voxels, each with its own coloured streak, kick, flash, cartridge cases and smoke: pistol (yellow), SMG (orange, hold to fire), shotgun (white, seven pellets, a pump), sniper (azure, right button or Z zooms three times through a scope and slows the mouse, one body shot kills a walker), grenade launcher (a lobbed ball that bursts in an area, hurting zombies and whoever stands near, never you; a drum that turns) and minigun (red, hold the button: the barrels spin up before it fires, then it never stops). The HUD is a game's and sits on the left so the "Altro" menu never covers it: health with a heart and a segmented bar, the weapon slots with their icons, the ammo, wave, kills and zombies on top. With a friend in the same office the shots, the weapon and HP travel with your position and both see the same paint. "Zombie" adds waves in a darker office with fog and failing lights, made of five kinds: walkers, runners (fast, thin, pale orange hoodie), brutes (wide, tough, a belly out of an apron), spitters (they keep their distance and spit goo that bursts where it lands) and, every fourth wave once the others are down, a boss with a health bar on top that slams the floor (jump over the shockwave). They walk to you along the real floor routes, the nearest of you and your friend, and never closer than about a metre and a half (a zombie inside the camera would be a green wall), and they are the same for everyone in the office: whoever started the mode runs them, the others see them and report their hits; a friend who did not start it is asked to join in first person or watch from above. A zombie run (its kills and wave) and the hits on a friend in paintball go to the leaderboards. The numbers are the tables in `scripts/office-guns.js` (weapons, models) and `scripts/office-zombies.js` (kinds, waves).
- **The arena**: paintball and zombies are played on a floor above the office, 4 m up, on the same 30 x 20 m plan and closed by walls and a ceiling with lights (`scripts/office-arena.js`): crates (0.6, 0.9 and 1.8 m), barrels, concrete barriers, columns, three raised platforms (1 m, with two steps each, climbed like the desks: walking up the steps, or Space in front of them), two long corridors with two openings each, an open area in the middle, and a base for each team, west (blue) and east (orange), with lit pads. You go up by the lift in the plaza (a core of steel and glass, E in front of it or a click: a choice of Paintball or Zombie) or by switching either mode on from "Altro", with half a second of black; E at the lift of the arena, in the west wall, or switching the mode off brings you back where you were. Up there the office below is hidden (fewer things to draw, and the TV, the radio and the lofi are not heard), and everyone who plays sees everyone: your height travels in your position (a friend who goes up appears 4 m higher, and only to whoever is up too). The zombies walk the floor of the arena along its real routes; from a platform you are higher, but their bite reaches 1.25 m and the goo and the shockwave of the boss reach you anyway (a jump saves you from the shockwave). The plan itself is plain data without a browser (`arenaPlan()`, `arenaWorld()`), so it can be checked in node: every base is free, there is a route from one base to the other and along the corridors, no pocket is closed, and the platforms can be reached by their steps.
- **The GitHub window**: on the north wall, between the task board and the live TV, a screen shows the project's open pull requests with the state of their checks, the last CI runs, the last commits and the open issues; E in front of it (or "Altro" > "GitHub", or a click) opens a panel with links. It reads the project with `gh` and `git` run in its folder, so the viewer must know the folder: `chat.py serve --repo DIR`, or `"repo": "DIR"` in the room's config; without it the screen is not there. The answer is cached for a minute (an old one is shown at once while a new one is fetched), every command has a time limit of 10 s, and a failure (no `gh`, not logged in, no network) is a short message on the screen. It is served at `/github.json` by the viewer only, never through the relay to friends (a repository can be private); only links to `https://github.com/` are kept.
- **Movements with a meaning**: an agent that posts a PLAN walks to the whiteboard to write it up; one that tags a colleague walks to the colleague's desk to say it (a review stays longer, looking at the screen); at most two walk about at once, and whoever is waiting for a permission, or in a meeting, keeps doing that.
- **The room chat for friends**: a switch in the panel (off by default) lets the friends linked to your common room read your room's own chat and write to everyone in it, text only. While a friend visits your office, that chat is the one their viewer shows; their lines count as yours for the agents (they answer at once, idle ones wake up).
- **Lending an agent**: a friend can ask for help; you approve or decline in the panel, choosing model, effort and minutes, and your lead spawns a helper that works for them. The helper also shows up in your friend's own chat and office, where they and their agents can tag it, and both sides can send it files. It works the other way too: from the panel you can ask a friend in your room for help, and they approve or decline on their side; their lead spawns the helper on their computer, and it appears in your chat and office as FRIEND·AIUTOn. A switch (off by default, with a model, effort and minutes to use) lends by itself, without asking, to the asks of friends and of the host, never more than two helpers at the same time. A lasting switch in the panel sets how far it goes: full help (the default: it works for real in its own folder, with commands, a venv, tests and cloned repositories) or cautious help (it only talks and writes drafts). Either way it never touches anything of yours outside that folder, and their request reaches it fenced as untrusted text.

Sharing survives restarts: the tunnel runs on its own, and the host keeps its port, PIN and guests in `common/share.json`, the guest its pass in `common/link.json`; restart either viewer and the friends stay linked, with no new PIN. Only Stop sharing (or Leave) ends it.

Only the common room ever leaves your computer. The viewer server stays on 127.0.0.1; sharing starts a separate server that answers only the common room's own routes, with the PIN tried at most 10 times in 10 minutes, a 48-character token per guest, and limits of 20 lines a minute, 10 documents an hour and 2 pending help requests per guest.

**cloudflared**: at the start of a session the plugin downloads `cloudflared` 2026.9.3 from Cloudflare's GitHub release into `~/.claude/chatroom/bin`, checked against its SHA256, unless it is already installed. It only runs when you share the common room through it.

## Using `chat.py` by hand

```bash
python scripts/chat.py init --room ./room --topic "My topic" --participants ALFA,BETA --user-name USER \
  --title "Design review" --icon "🧩" --accent "#6c5ce7" --profile "ALFA|🦊|#e84393|architect"
python scripts/chat.py config --room ./room theme=dark --profile "BETA|🐢|#16a085|skeptic"
python scripts/chat.py serve --room ./room --port 8765
python scripts/chat.py read --all --room ./room
python scripts/chat.py transcript --room ./room --out ./room/transcript.md
```

The room is a folder holding `chat.jsonl` (one JSON message per line), `config.json`, `roster.json` (name to agent ID, or to agent path in Codex), an `images/` folder for the pictures, and one read cursor per participant. Nothing is sent anywhere else.

## Codex

The plugin also installs in [Codex](https://developers.openai.com/codex) (CLI and app), from the same repository:

```bash
codex plugin marketplace add Partido-De-What/claude-plugins
codex plugin add chatroom@artyomita-plugins
```

Then start a new thread and ask for a chatroom. What changes from Claude Code:

- the lead spawns the agents with `spawn_agent`, one per participant, named after them in lower case; the roster holds their paths (`/root/name`), and `chat.py` then tells everyone to ping with `send_message` instead of SendMessage;
- Codex has no Monitor tool, so the lead stays in a loop until the chat closes: `wait_agent`, then `chat.py alerts` to relay what you write in the viewer, then `chat.py status`;
- an agent whose turn has ended wakes with `followup_task`, not with `send_message`;
- on Windows Codex runs PowerShell, which has no heredoc: the agents post with a single-quoted here-string, after `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)`, without which Windows PowerShell 5.1 turns accented letters into `?`. With the MCP server added once (`codex mcp add chatroom -- python <plugin>/scripts/chat.py mcp`) they call `chat_post`, `chat_read` and the board tools instead, with no quoting at all;
- the viewer is a local server: Codex's sandbox may ask you to approve it.
- the office, the common room, sharing and lending work the same. In a room of Codex agents the lending panel offers Codex models (`default` is your session's model) and effort up to `xhigh`, and the lead spawns the helper with `spawn_agent`;
- Codex runs no plugin hooks: the skill starts the cloudflared download when it opens the room, and `/stanza` exists only in Claude Code;
- sharing needs the network: if Codex's sandbox blocks it, approve the command when asked or give the sandbox network access;
- Claude Code and Codex mix: a Claude Code room and a Codex room can share the office on one computer, and a Codex user can join a Claude Code user's common room, play there, and lend or borrow agents (only the common room travels between them).

Subagents must be enabled in Codex (they are by default in current versions).

## Requirements

Python 3.8 or later, no packages. It works on Windows, macOS and Linux, in Claude Code and in Codex. Research rooms and `--merge-into` need `git` (2.38 or later for the merge check). Sharing the common room uses `cloudflared` (downloaded by the plugin) or `ssh` (for Pinggy).

## Cost

Every agent is a full model instance, and a lively chat with three agents easily reaches dozens of messages each. Use it for discussions worth that price.
